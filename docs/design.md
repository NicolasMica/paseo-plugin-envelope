# Envelope design

Design from the /office-hours session of 2026-10-08. The issues on the [Envelope board](https://github.com/users/NicolasMica/projects/4) derive from it.

## Problem

Paseo agents need environment variables, mostly secrets (API tokens and keys), without every developer hacking their shell. The usual workaround is a shell startup file that sources a `.env`. It only works in that shell, it can't be shared, and the variables only reach shell commands: not the agent process, not its MCP servers.

## Verified constraints (Paseo 0.11)

From the plugin docs, and from the spike in #3 (live daemon 0.11.1 and its bundled source):

- `server.before("agent.session_open")` runs on create, resume, refresh and import. The request has `agentId`, `workspaceId`, `provider`, `cwd`, `reason`, `purpose` and `env`, and only `env` is editable. `env` is an override map that excludes the daemon's inherited environment, and it is not persisted.
- On `create`, `request.env` holds only the env of the create request (`paseo run --env`), after `agent.create` hooks. On `resume`, `refresh` and `import` it is empty: Paseo doesn't persist create-time env, so it is gone at the next session opening.
- The provider env (`agents.providers.<provider>.env` in `config.json`) is not in `request.env`. The final env stacks the daemon's environment, then the provider env, then `request.env` after hooks, then `PASEO_AGENT_ID` and `PASEO_AGENT_CWD`, so a key the plugin adds overrides the provider env.
- `paseo.config.get()` from the hook context returns `providers.<provider>.env`, and `request.provider` is the bare provider id that keys it. A custom provider that `extends` another merges the base provider's env with its own, but `config.get()` returns each provider's own env, not the merged one.
- Paseo doesn't log the hook payload or the final env at the default `info` level (checked with sentinel values in `daemon.log`). At `trace`, it logs raw provider events, tool output included, so a secret an agent prints lands in `daemon.log`. At any level, it also stays in the provider's own transcript (see #19).
- A plugin's stdout and stderr go to `daemon.log` at `info` and to `paseo plugin logs`. A failing `before` hook's error message is logged at `error` and shown in the app.
- On OpenCode, any launch env key other than `PASEO_AGENT_ID` and `PASEO_AGENT_CWD` makes Paseo start a dedicated OpenCode server for the session instead of the shared one.
- `server.before("agent.create")` can add `mcpServers` (stdio or http), but only at creation. Its request is `{ config: AgentSessionConfig, env? }`: `config.provider` is the bare provider id that keys `agents.providers`, and `env` is the create request's env (`paseo run --env`, the app), undefined for the MCP `create_agent` tool and schedules. After the hooks, that `env` becomes `request.env` of the following `agent.session_open`. The hook runs before Paseo's `prepareSessionConfig`, which then adds the host `daemon.appendSystemPrompt` (Settings → Orchestration → Append system prompt) as a separate part, so providers get `<config.systemPrompt>\n\n<daemon append>`. Paseo sets no default `config.systemPrompt` (schedules copy their own, voice mode rewrites it). The post-hook `systemPrompt` is persisted with the agent and re-applied on resume and refresh. `agent.create` hooks don't run on resume, refresh or import, nor for internal agents (`config.internal`, such as branch-name or commit generation). When a stored agent has no provider persistence handle, loading it re-runs `createAgent` with the stored config and an undefined `env`.
- Providers apply `systemPrompt` differently. Claude Code: `systemPrompt: {type: "preset", preset: "claude_code", append}`, appended to its system prompt and re-sent on every query, resume included. Codex app-server: `developerInstructions` on `thread/start`, `thread/resume` and every `turn/start` (a developer message), appended after a collaboration mode's own developer instructions. OpenCode: `system` on each prompt (legacy) or a session instruction entry keyed `paseo` (v2). Pi: appended through a generated extension. OMP: `--append-system-prompt`. Plugin providers receive it combined. ACP-based providers (Copilot, Cursor, Kimi, Kiro, Trae, generic ACP, Gemini through ACP) ignore it.
- Several `before` hooks of one plugin run in registration order, each seeing the previous result, and returning `undefined` keeps the request.
- No API lets a plugin host an MCP server or add a subcommand to the `paseo` CLI.
- `defineSettings` stores plain JSON on the host ("not a credential vault").
- Plugins are disabled by default: everyone has to enable them once in Settings → Plugins. Install with `paseo plugin install github:owner/repo`, update with `paseo plugin update`.
- Hooks time out after 30 s, and a failing `before` hook fails the session opening.

## Decisions

- **V1 = a single global `.env`**: no project level, no MCP. Its path is configurable with one plugin setting, `envFile`, in the host settings document `settings` (`shared/settings.ts`, stored at `<paseoHome>/plugin-settings/<pluginInstallId>/settings.json`), edited from the Settings screen (#36) or by hand. We use plugin settings because the Settings screen edits them with the host's `useSettings`, and because the plugin's entry in `config.json` has a strict schema that can't hold extra fields. The store validates with the plugin's own zod schema; Paseo supplies `zod` to server code, so it stays a dev dependency. `read()` re-reads the file on every call, so the hook reads the settings on every session opening and an edit applies at the next one. A set `envFile` is used as is after expanding a leading `~`; it must be absolute, otherwise the hook warns and injects nothing. A missing file gets a warning. There is no default path (#40): with `envFile` empty or absent the hook returns the request unchanged, reads nothing and logs nothing, so a file can't start injecting into every agent without the user having chosen it. Earlier versions read `${XDG_CONFIG_HOME:-~/.config}/paseo-plugin-envelope/.env` when the setting was empty; anyone who relied on it must set `envFile` to that path. Invalid settings or a failed read inject nothing, and the invalid state's `error` is not logged because it can quote stored values.
- **Settings screen** (#36): `index.client.tsx` registers one `addSettingsScreen` screen (Settings → Plugins → Envelope → Environment). `client/settings-screen.tsx` reads the settings with `useSettings` and handles the `loading` (renders no value, so no default passes for a saved one), `error` (reload) and `invalid` (reset) states itself, then renders a list of sections that each receive the ready settings (`client/section.ts`). This step adds `client/env-file-section.tsx`; the variable list (#12) and the add-variable form (#37) add their own sections to that list. The path field is a draft editor on `SettingsInput`: the values and revision are captured when editing starts and saved with that revision, so a save over another client's change is refused as a conflict and the user can reload; an empty (trimmed) path removes the key. `saving` and `saveError` belong to the whole settings document, so a section shows `saveError`, and offers Reload instead of Discard, only after its own save failed. The input is remounted with the saved path after a save, a discard, or a change saved elsewhere while there is no draft, never mid-edit. A light client-side check (`~`, `~/…`, `/…`, `X:\`, `X:/`, `\\…`) blocks obvious mistakes; the daemon's status stays the authority. A **Browse** row opens the daemon file browser (see File browser below) and fills the field as a draft. The screen only uses the host's settings components, so it renders no custom `Text` and takes no color of its own.
- **File status RPC** (`env-file.status`, `shared/env-file-status.ts`, `server/env-file-status.ts`): empty input, and a discriminated union on `state`: `ok`, `missing` (`ENOENT` or `ENOTDIR`), `not-file` (directory, FIFO, socket, device), `error` with an identifier-shaped `code` or `UNKNOWN` (including `EACCES` for a regular file the daemon can't read, and `ETIMEDOUT`), each with the `path`, plus `unresolved` with only a `code` when resolving the path throws (`homedir` without a home directory), and `not-configured` (empty or absent `envFile`), `relative`, `invalid-settings` and `settings-unreadable`, which carry nothing. The client shows `not-configured` as a plain status, not an error. The handler never rejects. It reads the saved settings server-side with the same `settings.read()` as the hook and resolves the path with the hook's `resolveEnvFile`, so it reports exactly the file the next session opening reads, not the unsaved draft. It `stat`s the path (following symlinks, like the hook's `open`) and, for a regular file, checks `access(path, R_OK)`, so a file the hook couldn't open (mode 000, another owner) isn't reported as found. It never opens the file, so it never reads content and can't block on a FIFO. Both calls run in one shared promise under the hook's 5 s `withTimeout`; concurrent checks of a path share it, so repeated refreshes on a stalled mount hold one threadpool thread. It never returns the settings' validation error, which can quote stored values. `withTimeout`, `errorName` and `errorCode` live in `server/errors.ts`, shared by the hook and the RPC, and the code shape is `ERROR_CODE` in the shared contract. The client runs it with `useRpc` and TanStack `useQuery` keyed on the settings revision, so it runs again after a save, with `retry: 1` (file problems come back as states, so a retry only covers transport), and offers Refresh for a file created later.
- **File browser** (#46, `env-file.browse`, `shared/env-file-browse.ts`, `server/env-file-browse.ts`, `client/env-file-browser.tsx`): a **Browse** row in the Environment file card opens a host `Modal` (bottom sheet on compact layouts, dialog otherwise) that lists the daemon's filesystem with host settings rows in the default scrolling `Modal.Content`, so it renders no custom `Text`, takes no color of its own and has one scroll owner. We chose a picker over suggestions while typing: it works the same with touch and a mouse, and is built only from host pieces, while suggestions would need an anchored dropdown the plugin UI kit doesn't provide, and need typing, which is what mobile users avoid. An OS file picker would browse the client's machine, not the daemon's, so it is wrong on mobile and remote clients. The picker opens at the directory of the current text (the draft if editing, else the saved path; the home when it is empty or fails the client-side check) and starts again from there on every opening. The current directory is a row, then **Up** (disabled at the root), then one row per entry: directories and symlinks to directories get **Open** and a trailing separator, files and symlinks to files get **Choose**, anything else (broken link, link not checked in time, socket, FIFO, device) is a plain row saying why it can't be chosen; a link not checked in time says so and suggests typing its path. Dotfiles are shown. Choosing closes the modal and fills the field as a draft without the input's imperative ref: the section sets the draft (keeping the values and revision captured when the draft started, or capturing them now when there was none) and remounts the input with the picked path as `initialValue`. Save still applies it against that revision, so a pick over another client's save is refused as a conflict like a typed change. Browse is disabled while saving. The RPC input is `{ path?, containing? }`: a blank path lists the home, `~` and `~/…` expand with the hook's own `expandHome` (extracted from `resolveEnvFile`, same behavior), a non-absolute path returns `relative`, and `containing` lists the path's dirname, except for `~` and a path ending in a separator, which name a folder and are listed themselves. With `containing`, a folder that is missing or not a directory, and a path that isn't absolute (a Windows-style draft on a POSIX daemon), fall back to the home, so the picker never opens on a dead end. The output is a union on `state`: `ok` with the absolute `path`, its `display` form (`~` or `~/…` under the home, else absolute), the `parent` in display form (null at the root), the daemon's `separator`, the entries and their `total`; `missing` (`ENOENT`), `not-directory` (`ENOTDIR`), `error` with an identifier-shaped `code` (`ERROR_CODE`, else `UNKNOWN`; `ETIMEDOUT` for a stalled `readdir`, `EBUSY` when too many operations are pending), `relative`, and `unresolved` when the home can't be resolved and the path needs it (an absolute path is still listed, shown absolute). The client joins a name onto `display` with the separator, without doubling it at the root, and with `/` onto `~`, the only home form the daemon expands. Entries carry a name, a kind (`file`, `directory`, `symlink`, `other`) and, for symlinks only, the `target` kind from `stat` (`missing` for a broken link or any stat error, `unknown` for a link that wasn't followed); never sizes, times, modes or content. They are sorted directories and symlinks to directories first, then by name with a fixed-locale (`en`), case-insensitive, numeric-aware `Intl.Collator`, ties broken by code point, and cut to `BROWSE_ENTRY_CAP` (500), with a row saying how many there were. A symlink's target can move it into the directories group, so symlinks are followed before sorting: one at a time, in name order, so a link into a stalled mount holds one libuv thread, not the whole threadpool the hook reads with. Each request has one 5 s deadline. The `readdir` (with file types) runs under it with `withTimeout`, and concurrent requests for a directory share one in-flight `readdir`, as the status check shares its check. The links are then followed with whatever is left of the deadline: a link not resolved before it, or past the first 500, gets `target: "unknown"` and sorts with the files, so one link into a hung mount can't fail the whole folder. Pending `stat`s are shared per link path, so a retry waits on the same hung `stat` instead of pinning another thread. The `stat`s are not part of the shared `readdir` promise, so a later request never joins a listing stuck behind a hung link. A global cap bounds the threads browse can pin: the handler counts its in-flight `readdir`s and `stat`s, decremented only when they really settle, not when a caller stops waiting. With 2 already pending (`maxPending`, an option for tests), a listing that needs a new `readdir` returns `error` with `EBUSY` without touching the filesystem (joining a pending `readdir` is still allowed), and a link `stat` that would exceed the cap is skipped as `unknown`. The plugin subprocess has 4 libuv threads by default, so at least 2 stay for the hook's `.env` read and the status check. The handler never throws and logs nothing. The client runs it with `useRpc` and TanStack `useQuery` keyed on the requested path, only while the modal is open, with `retry: 1`; a transport failure offers Retry. No state is a dead end: `error` offers Retry (an `EBUSY` or `ETIMEDOUT` can pass), plus Go to home when the failing location isn't the home; `missing`, `not-directory` and `relative` offer Go to home, or Retry when the location already is the home, where Go to home would ask for the same listing again.
  - **What a remote client can learn**: any client connected to the daemon can list any directory the daemon user can read: entry names, their kinds and the kinds symlinks point to, whether a path exists (`missing` versus `EACCES` tells "exists but unreadable" apart), and the home directory's absolute path through `path`. It never gets file content, sizes or times. This adds no capability beyond what such a client already has, since it can run agents with shell access as that user, but names can themselves be sensitive (project and client names, file names), so the handler logs nothing. The RPC handler receives no caller identity, so the plugin can't restrict listings per client or tell clients apart; the only bound is global, the pending-operations cap above, which keeps any client from pinning more than 2 of the plugin's threads on a hung mount at the cost of `EBUSY` for everyone until they settle.
- Variables are injected when a session opens. An agent that is already running only sees a change after it is resumed or refreshed.
- Values are stored in plain text in a file. Keychain and 1Password come later.
- The CLI is out of the ideal version as long as Paseo doesn't allow extending its CLI.
- Explicit env keeps the last word over the `.env`: a `.env` key is injected only if it is absent from `request.env` and from the env of the agent's provider, including the providers it `extends`, read with `paseo.config.get()`. Paseo applies `request.env` after the provider env, so relying on `request.env` alone would let the global `.env` overwrite a provider's explicit env (#3). Codex suggested letting the `.env` win; we keep this order so that a global `.env` never overwrites the explicit env of a create request or of a provider. Two limits: the `.env` does override the daemon's inherited environment, except for the protected keys (`PATH`, `HOME`, `SHELL`, `USER`, `PASEO_*`), and a key passed with `paseo run --env` only wins at create, because Paseo drops it at the next session opening and the `.env` value then applies.
- The hook (`server/inject-env.ts`) reads the file `resolveEnvFile` returns for the `envFile` setting: the path with a leading `~` expanded, `undefined` when the setting is unset or empty, `null` when it isn't absolute. It follows the `extends` chain the way Paseo does: it stops at `acp`, at an unknown base and on a cycle, and ignores `extends` on a built-in provider (Paseo silently ignores it there, getpaseo/paseo#3178). It learns which ids are built-in from `paseo.providers.snapshot()`, whose entries carry `source: "builtin"`, instead of hardcoding a list that would drift from the daemon's; an id missing from the snapshot is followed, which can only skip more keys, never overwrite one. `paseo.config.get()` and `paseo.providers.snapshot()` run in parallel, each with its own 5 s timeout, well under the 30 s hook timeout that would fail the session opening. When `config.get()` fails or times out the hook injects nothing. When the snapshot fails, times out or is malformed, the hook warns and walks as if no provider were built-in, so a snapshot problem never blocks injection. It warns when the file is group- or world-readable, once per file state, and on any error returns the request unchanged. It opens the file with `O_NONBLOCK`, so a FIFO with no writer can't hang the session opening, and rejects anything that isn't a regular file with `EISDIR` or `ENOTREG`. The whole read (`open`, `stat`, `readFile`, `close`) has its own 5 s timeout, so a regular file on a stalled network mount or hung FUSE filesystem logs `read failed: ETIMEDOUT` and injects nothing instead of hitting the 30 s hook timeout. A libuv thread blocked in the read can't be cancelled, so the hook stops waiting rather than abort it, and doesn't pass it the hook signal: Paseo only aborts once it stopped waiting, and the read is already bounded. While a read of a path is still in flight, later session openings wait on that same read instead of starting another, so a stalled mount holds one threadpool thread, not one per session opening. Logs never contain a key name, only counts: one line per session opening, `<agentId> (<reason>) injected N`, followed by `, skipped M protected` and `, K already set` when non-zero, as soon as the file has a key. This follows dotenv's own `config()`, which only logs `injected env (N) from <path>`, and a malformed file can turn a value fragment (the last line of an unquoted multi-line base64 value, a pasted token ending in `=`) into a key, so any logged name could be a value. Error names and codes are only logged when they have an identifier shape (`^[A-Za-z][A-Za-z0-9]{0,63}$` and `^E[A-Z0-9]{1,31}$`), else `Error` and `UNKNOWN`, so a crafted error can't carry a value into the logs either.
- The `.env` is read with `dotenv`'s `parse` (default parser), wrapped by `parseEnvFile` in `server/env-file.ts`. We don't write our own parser, to avoid maintaining one. Unlike `util.parseEnv`, dotenv bundles its own pure-JS parser, so the same file gives the same result whatever Node version runs the plugin. It does no `$VAR` interpolation (that is `dotenv-expand`, which we don't use) and no command substitution, and `parse` never throws on content and never logs. The result is a plain object, so a key like `hasOwnProperty` shadows the method: read it with `Object.entries` or `Object.hasOwn`. We accept its rules as they are and pin them with tests: `KEY: value` is accepted, `#` starts a comment even without a space before it, single quotes, double quotes and backticks are all quotes, double quotes expand `\n` and `\r`, quoted values can span lines, keys may start with a digit and contain `.` and `-`, and lines that aren't an assignment are skipped silently. A broken quote is not skipped: `KEY="abc` with no closing quote, or `KEY="abc" junk`, keeps the raw text, quotes included. dotenv gives no line numbers, so the plugin reports no per-line warning: rebuilding one would mean scanning lines ourselves, which is the parser we chose not to write.
- Dependencies use caret ranges, not exact pins: the committed lockfile already gives every install the same versions, and the tests catch a `dotenv` update that changes parsing. For supply-chain safety, `.npmrc` sets `min-release-age=7`, so `npm install` and `npm update` only pick versions published at least a week ago. It doesn't affect `npm ci` from the lockfile. A fresh resolution fails while a pinned dependency is younger than a week (`@getpaseo/plugin` 0.11.1 until 2026-10-14).
- The plugin is installed from Git, so `paseo-plugin.json` declares `build: npm ci --omit=dev --ignore-scripts` to install `dotenv` from the committed lockfile. `--ignore-scripts` skips the root `prepare` script (`lefthook install`), which would fail without dev dependencies. This step assumes Git installs: an npm package ships no lockfile, so `npm ci` would fail there, and Paseo already installs an npm package's dependencies. Remove it if the plugin is ever published on npm. A registry listing pins a Git tag, so it installs the same way as Git.
- Quality gates (#31) are `tsc --build`, type-aware oxlint (`correctness`, `suspicious`, `perf` and `pedantic` plus the `vitest` plugin; warnings, unused disable directives, disables that name no rule, focused or skipped tests and any comment naming a coverage tool fail), oxfmt, and Vitest with v8 coverage at 100% over every `ts`, `tsx`, `mts`, `cts`, `js`, `jsx`, `mjs` and `cjs` file in the repo, tested or not, except tests, `.d.ts` files, root `*.config.*` files, `coverage/` and `node_modules/`; `.only` also fails the run. The pre-commit hook runs the same four commands on the whole working tree, and CI runs them on the pushed commit. The TypeScript options follow the Total TypeScript cheat sheet for code a bundler compiles (Paseo's esbuild), with `allowJs` plus `checkJs` so a `.js` source is checked as strictly as TypeScript, plus `exactOptionalPropertyTypes`, `noImplicitReturns`, `noFallthroughCasesInSwitch`, `noPropertyAccessFromIndexSignature`, `noUnusedLocals` and `noUnusedParameters`. `skipLibCheck` stays on because zod's declarations use the `URL` global, which the client side (no DOM, no Node) doesn't have. The server and the client run on different runtimes, so `tsconfig.json` is a solution file with three projects on a shared `tsconfig.base.json`: `tsconfig.server.json` (Node types: every source file except `client/` and `index.client.*`, so a stray script is checked too), `tsconfig.client.json` (React types only, no Node, no DOM: `index.client.*`, `client/`, `shared/`, without tests), so `shared/` is checked against both, and `tsconfig.client-test.json` (Node and React types, for client tests, which run in Vitest). Client tests render with `test-renderer`, the maintained React 19 renderer that React Native Testing Library builds on, pinned to `~1.1.0` because that line uses `react-reconciler` 0.32, which matches the host's React 19.1 (1.2 and 1.3 need React 19.2 and 19.3). The real `react-native` can't load under Vitest and `@getpaseo/plugin/client/ui` ships no runtime, so the tests mock `@getpaseo/plugin/client` (`useSettings` on a small external store, `useRpc` returning a stub) and `/client/ui` (host elements named after each component, read and pressed through their props), and use a real `QueryClientProvider`. The `useRpc` stub dispatches by contract name and parses the input and output with the contract like the real one, so fixtures are checked against the schema. `@getpaseo/plugin/client/react-native` is mocked too: `Modal` renders its children in a `Modal` host element only while `open`, exposing `onOpenChange`, and `Modal.Content` is a host element. Each test file keeps its own small harness, since a shared helper module would count toward coverage. The root also extends the base so esbuild, which reads the nearest `tsconfig.json` without following references, sees the same options.
- The repository is public so anyone can install the plugin with `paseo plugin install github:NicolasMica/paseo-plugin-envelope`, without being a collaborator (#58). CI runs on GitHub-hosted `ubuntu-latest` only, never on a self-hosted runner, because a workflow on a public repo runs pull request code on whatever machine runs the job. The workflow token is read-only (`permissions: contents: read`), checkout doesn't persist credentials, and actions are pinned by commit SHA; Dependabot updates the pins with a 7-day cooldown, the same delay as `min-release-age`. `.npmrc` sets `ignore-scripts=true`, so checking out a branch and running `npm ci` (Paseo's worktree setup, a Dependabot PR) runs no dependency install script; `npm run prepare` installs the pre-commit hook once per clone. Vulnerabilities are reported through GitHub private vulnerability reporting (`SECURITY.md`).
- A `server.before("agent.create")` hook appends a fixed secrets-handling guideline (`SECRETS_GUIDELINE` in `server/guideline.ts`) to `config.systemPrompt`, only when the session would inject at least one variable (#19). Both hooks come from `createEnvelopeHooks` in `server/inject-env.ts`, follow the same `envFile` rule (unset means no read, no log and no guideline), and share one core, `computeInjection(provider, explicitEnv)`, that reads the settings and the file, parses it, drops protected keys and keys in the explicit env and the provider `extends` chain, so the two hooks can't disagree; they also share the pending-read dedupe. The create hook passes `config.provider` and an empty explicit env, ignoring the create `env`: Paseo drops a `paseo run --env` key at the next session opening, where the `.env` value then applies, so an agent whose create env shadowed every key would get the secrets on resume without the guideline. It asks "would a resumed session of this provider get at least one key", so only the provider env chain and protected keys can suppress the guideline. The check happens once: an agent created while the `.env` was missing or empty, or while its provider env set every key, never gets the guideline, even if it receives variables later. Each hook bounds its own wait on the shared read (5 s each) and its own config read (5 s), so a stalled mount can delay creation by up to about 20 s in total, still under each hook's 30 s limit; and if the read settles between the two hooks' deadlines, session_open can inject while the create hook already skipped the guideline. Accepted for V1 rather than caching results across hooks (#45). It is silent: no log line and no warning, and it doesn't touch the permission-warning state, because the session_open hook runs right after for the same file and logs and warns once. On any failure it returns the request unchanged, without the guideline. A non-blank prompt becomes `<prompt>\n\n<guideline>`, a blank or missing one becomes the guideline. It skips a prompt that has a line that is exactly the guideline heading, `## Environment secrets` (`SECRETS_GUIDELINE_HEADING`, ignoring surrounding whitespace), since an agent reloaded without a provider handle is re-created from its stored, already appended prompt; matching the heading rather than the full text keeps a reworded future guideline from being appended a second time. Appending to `config.systemPrompt` keeps the agent's own prompt first and Paseo's Append system prompt after it. The guideline names no variable: the prompt is fixed at creation and would go stale, and names could carry a value fragment (see the logging decision). It only reaches agents created after the plugin is enabled, since `agent.session_open` can only change `env`. It is guidance, not a guarantee.

## Rejected approaches

- **Full platform from the start** (UI, MCP and inspector): too much surface before the core is validated. It becomes the roadmap (P2).
- **Our own `.env` parser**: full control over the rules, but code to maintain for a need `dotenv` already covers.
- **Delegating to direnv** (`direnv export json`): forces direnv and `direnv allow` on every colleague, and runs shell code on every session opening.

## Risks

- High: values leaking through logs. The plugin's output goes to `daemon.log`, and a hook's error message is logged and shown in the app, so the plugin never logs a key name or a value, only counts, paths, error names and error codes restricted to identifier shapes, including in error paths and thrown errors.
- High: broad exposure. The global `.env` goes to every agent, of every provider. Accepted for V1; scoping comes in V2.
- Medium: stdio MCP servers. Tested in #6: Claude Code passes the agent's environment to them, Codex starts them with a minimal environment plus the server's `env` and `env_vars`. The README documents it rather than promising inheritance.
- Medium: providers copy the environment elsewhere. Codex keeps a snapshot of the shell environment, values included, in `~/.codex/shell_snapshots/` (#6). It deleted the probe agents' snapshots when they were archived, but an older one with no live Paseo agent remained, and the snapshot also bypasses `shell_environment_policy`. Documented in the README; the plugin can't prevent it.
- Medium: surprising precedence when a variable is removed, or when a resume or refresh drops a `paseo run --env` key and the `.env` value takes over. We test it and document it.

## Long-term vision

A colleague installs the plugin, opens any checkout, and their agents get the right credentials for that project. The app shows the loaded variables, where they come from, and which ones are missing compared with the repo's `.env.example`.
